# AI-Powered Music Curator — Product & Engineering Spec

> **Working title:** AI Powered Music Curator *(final name TBD)*
> **Status:** Draft v1 — September 2026
> **One-liner:** A web app that interviews you with ~12 smart, adaptive questions and curates a personalized ~25-song playlist where every track links straight to Spotify, YouTube, or Apple Music.

---

## 1. Overview

Users answer a conversational quiz. An LLM adapts each follow-up question based on previous answers (e.g., say you love metal → it asks about subgenres). At the end, the LLM proposes a tracklist, the backend **validates every track against real music APIs**, resolves **deep links** to Spotify / YouTube / Apple Music, and presents the playlist as clickable cards. Users can sign in (Google or email) to save playlists, and every playlist gets a **shareable public link**.

**Core principle:** never show a song that doesn't exist, and never show a link that 404s.

---

## 2. Goals & Non-Goals

### Goals (MVP)
1. Fully adaptive quiz experience (10–12 questions), AI-generated follow-ups.
2. ~25-song playlist per run, validated track-by-track.
3. Deep links to Spotify, YouTube/YT Music, Apple Music (exact song when resolvable, search URL as fallback).
4. Accounts: Google OAuth + email/password.
5. Shareable public playlist URLs.
6. Runs entirely on free tiers (LLM, music APIs, hosting).

### Non-Goals (for now)
- ❌ Audio streaming inside the app (we link out only — avoids licensing issues).
- ❌ One-click "export playlist to Spotify/Apple" (needs platform OAuth; v1.1+).
- ❌ Native mobile apps (responsive web first).
- ❌ Social features (comments, follows) — later.
- ❌ Real-time collaborative playlists.

## 4. Functional Requirements

| ID | Requirement |
|----|-------------|
| FR-1 | Quiz consists of **10–12 questions**; at least 10 must be asked before generation unlocks. |
| FR-2 | Questions are **fully adaptive**: each next question is generated by the LLM from the answer history, constrained by a question-type schema. |
| FR-3 | Question types: single-choice, multi-choice, 1–10 scale, free text. All AI-generated questions are schema-validated server-side. |
| FR-4 | Playlist length defaults to **25 tracks** (30 candidates requested to survive validation drops). |
| FR-5 | Every track is validated against at least one music API before display; tracks with zero matches are dropped and replaced (up to 2 LLM retry rounds). |
| FR-6 | Each track card shows three platform buttons: Spotify, YouTube, Apple Music. Exact deep link when resolved; platform search URL as fallback. |
| FR-7 | Auth: Google OAuth **and** email+password. Anonymous users can complete quizzes; saving requires an account (quiz can be claimed on signup). |
| FR-8 | Every generated playlist has a public share URL (`/p/:shareId`) viewable without login. |
| FR-9 | Playlist page shows: title (AI-generated), vibe summary (2–3 sentences), tracklist, share button. |
| FR-10 | Track metadata (cover art, album, year, preview availability) is cached permanently in a track cache table — APIs are hit at most once per unique track, ever. |
| FR-11 | Rate limiting + per-IP daily quiz quotas to protect free tiers from abuse. |

## 5. The Adaptive Quiz Engine

- **Flow:** client sends `answers[]` to `POST /api/quiz/next` → server builds a prompt containing the answer history → LLM returns the next question (JSON, schema-validated) → repeat until `questionCount >= 10` and the LLM returns `{"done": true}`.
- **Guardrails:**
  - Hard cap of 12 questions; min 10 before done is accepted.
  - Server-side system prompt defines the question *arc*: warmup (genres, eras) → deep-dive (subgenres, moods, artists) → context (activity, setting, language, discovery-vs-comfort) → curveballs (guilty pleasures, hate-lists) → wrap-up.
  - No repeated question *topics*: the prompt includes asked-topic tags, and the schema forces a new `topic` tag each time.
  - All options are generated fresh; schema-validated (2–6 options, non-empty strings).
- **Free-text answers** are allowed but optional; scale questions map to audio-energy descriptors.

## 6. Playlist Generation Pipeline

```
answers[] ──> Prompt builder (profile summary)
                 │
                 ▼
        LLM: propose 30 candidate tracks
             (title, artist, ~year, reason_1_line, confidence)
                 │  JSON schema-validated
                 ▼
        Validator (parallel, concurrency 5)
             for each candidate:
               1. Deezer public API search  (no key, 50 req/5s)
               2. iTunes Search API          (no key, ~20 req/min)
               → keep best match (artist+title fuzzy match ≥ threshold)
                 │
                 ▼
        Deep-link resolver (per kept track, results cached forever)
               • Apple Music: iTunes API `trackViewUrl` → exact link ✅
               • YouTube: YouTube Data API v3 search (free quota, cached)
                 → exact video link ✅
               • Spotify: exact track URL when resolvable; otherwise
                 https://open.spotify.com/search/<query> (opens app pre-filled)
                 │
                 ▼
        Score + reorder (LLM confidence × match quality)
        Backfill: if < 25 kept, one LLM retry round with "avoid: dropped list"
                 │
                 ▼
        Persist playlist + tracks (track cache dedupe by normalized identity)
```

**Match rules:** normalize case/punctuation; require artist surname/token match AND title ≥ 85% similarity (Levenshtein or token overlap). Prefer the version matching the requested era/type (studio vs live, original vs remake).

## 7. Auth & Accounts

- **Google OAuth 2.0** (authorization code flow) + **email/password** (bcrypt, cost ≥ 12).
- Sessions: JWT access token (15 min) + refresh token (30 d, rotating, httpOnly secure cookie).
- Anonymous quiz → on signup/login, quiz session is claimed via a signed quiz-token cookie/localStorage.
- New table rows are user-scoped; anonymous sessions are kept for 7 days then purged.

## 8. Sharing

- `shareId`: 10-char nanoid (URL-safe), separate from internal UUID.
- Public playlist page is server-rendered metadata (OG tags: title, description, cover collage) so links preview nicely in chat apps.
- "Copy link" button + native share sheet on mobile.

## 9. Data Model (PostgreSQL)

```
users            id uuid PK · email unique · password_hash? · google_id? · name · avatar_url · created_at
quiz_sessions    id uuid PK · user_id? FK · status(active|generating|done|failed) · answers jsonb · created_at
playlists        id uuid PK · share_id unique · quiz_session_id FK · user_id? FK · title · vibe_summary · created_at
playlist_tracks  playlist_id FK · position int · track_id FK · match_status(exact|fallback) · reason text
track_cache      id uuid PK · fingerprint unique (normalized artist+title+year) · title · artist · album · year
                 · cover_url · preview_url? · isrc? · links jsonb {spotify, youtube, apple, deezer}
                 · verified_at · source(deezer|itunes)
```

## 10. Architecture & Stack

**Monorepo (pnpm workspaces + TypeScript everywhere):**

```
music-curator/
├─ apps/
│  ├─ web/      React 18 + Vite + Tailwind CSS + framer-motion + TanStack Query + react-router
│  └─ api/      Node 20 + Express + Prisma + zod
└─ packages/
   └─ shared/   Shared types + zod schemas (Question, Track, Playlist DTOs)
```

| Layer | Choice | Why |
|---|---|---|
| LLM | **Gemini API free tier** (Flash model) primary, **Groq free tier** fallback — behind one provider interface | Both free, both support structured JSON output; swappable via env var |
| Music validation | Deezer public API + iTunes Search API | Keyless, free, complementary catalogs |
| YouTube links | YouTube Data API v3 (free 10k units/day) + permanent cache | ~100 searches/day free; cache makes it once-per-track-ever |
| DB | PostgreSQL (Render free tier) | Relational fit, Prisma migrations |
| Auth | google-auth-library + bcrypt + JWT | No heavy framework needed |
| Hosting | Web → Vercel · API + DB → Render (free) | Matches user preference |

### API endpoints (v1)

```
POST /api/quiz/start              → { sessionId, firstQuestion }
POST /api/quiz/next               → { nextQuestion | { done: true } }
POST /api/quiz/generate           → { playlistId } (202; SSE/GET for progress)
GET  /api/playlists/:id           → full playlist (auth: owner or public)
GET  /api/share/:shareId          → public playlist
POST /api/auth/register|login|google|refresh|logout
GET  /api/me/playlists            → user's library
```

## 12. Free-Tier Budget & Abuse Protection

| Resource | Free allowance | Protection |
|---|---|---|
| Gemini free tier | ~hundreds of req/day (RPM-capped) | 3 LLM calls per quiz max (next-question calls are tiny; generate = 1–3 calls). Per-IP: 3 quizzes/day |
| Groq free tier | RPM/RPD capped | Automatic fallback when Gemini 429s |
| Deezer | 50 req / 5 s | Concurrency 5 + backoff; permanent cache |
| iTunes Search | ~20 req/min | Concurrency 2 + cache |
| YouTube Data API | 10k units/day (search = 100 units) | Cache-first; search once per unique track ever (~100 new tracks/day) |
| Render/Vercel free | Instance sleeps; fine for MVP | — |

## 13. MVP Milestones

1. **M1 — Skeleton:** monorepo, CI typecheck, DB schema + migrations, health endpoint.
2. **M2 — Quiz loop:** quiz engine + adaptive questions + quiz UI with animations.
3. **M3 — Curation core:** LLM candidates → validation → deep links → playlist page. *This is the heart — build and tune until link quality is ≥ 95% exact.*
4. **M4 — Auth + persistence:** Google + email auth, saved library, share URLs with OG tags.
5. **M5 — Polish:** rate limits, error states, empty states, mobile pass, deploy.

## 14. Risks & Mitigations

| Risk | Mitigation |
|---|---|
| LLM hallucinates songs | Validation-first pipeline; dropped tracks replaced; never render unverified tracks |
| YouTube quota exhaustion | Permanent cache; degrade to YouTube *search URL* fallback (no quota cost) |
| Spotify exact links need OAuth now | v1 ships Spotify search-URL buttons; revisit OAuth "add to Spotify" as v1.1 feature |
| iTunes rate limit on burst generation | Queue at concurrency 2; cache; Deezer does the heavy lifting |
| Free LLM rate limits under load | Provider fallback chain + per-IP quotas + queue |
| API changes (unofficial/quirky endpoints) | Both music sources are official public APIs; abstract behind `MusicResolver` interface |
